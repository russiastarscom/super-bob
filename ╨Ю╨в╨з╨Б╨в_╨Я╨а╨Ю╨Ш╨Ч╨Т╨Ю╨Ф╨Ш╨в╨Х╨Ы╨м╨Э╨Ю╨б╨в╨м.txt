ЧТО СДЕЛАНО
───────────
1. ДВА C++-ДВИЖКА, СКОМПИЛИРОВАННЫХ В WEBASSEMBLY (engine/bob_engine.cpp)
   C++ выполняется в браузере телефона только через WebAssembly — это
   стандартный путь (Emscripten). Написаны два движка в одном WASM-модуле:

   • bobphys — движок коллизий и физики:
     - сетка тайлов уровня хранится в линейной памяти WASM (без GC),
     - толкаемые камни — SoA-массив, синхронизируется из игры,
     - solid-запросы (solidPx) и проходы moveX/moveY переехали в C++,
     - семантика ПОБАЙТОВО та же, что у исходного JS: те же формулы,
       округления Math.floor, отступы 0.01, тот же выбор тайла для бампа.

   • bobfx — движок частиц (Structure-of-Arrays):
     - фиксированный пул на 240 частиц (как прежний потолок L.parts),
       все поля в типизированных массивах, НОЛЬ аллокаций в кадре,
     - спавн — вызов fx_spawn; шаг всех частиц — ОДИН вызов fx_step(dt),
     - рендер читает Float64Array/Uint8Array-виды прямо из памяти WASM
       (раньше: 240 объектов × 60 кадров/с = ~14 тыс. обращений к
       свойствам объектов в кадр + splice-мутации + мусор для GC).

2. JS-ДВОЙНИК (engine/bob_twin.js)
   Точная копия обоих движков на JS. Если WASM недоступен (старый
   браузер, сбой) игра автоматически работает на двойнике — и он же
   служит эталоном в тесте эквивалентности.

3. КЛЕЙ ENG (engine/bob_glue.js)
   Игра общается только с window.ENG; клей выбирает WASM или JS-двойника,
   первый кадр стартует после готовности движка (задержка ~миллисекунды).

4. ИНТЕГРАЦИЯ В ИГРУ (tools/patch_index.py, применяется к index.html)
   - solidPx, moveX/moveY — тонкие обёртки над ENG;
   - все 21 место спавна частиц работают через адаптер L.parts -> пул
     движка (код спавнов не изменён — ноль правок геймплейных чисел);
   - 3 цикла обновления частиц заменены на ENG.fxStep(dt);
   - 2 цикла рендера частиц читают массивы движка напрямую;
   - синхронизация сетки (решётки, мостики, замки, блоки '?') и камней
     (оседание, толкание Бобом) зеркалится в движок — позиции всегда
     актуальны внутри кадра, как в оригинале;
   - режим АРЕНА подключён так же, как основная игра.

5. УМНЫЙ КЕШ НА PYTHON (tools/smartcache.py)
   Каждая дорогая стадия сборки кешируется по SHA-256 входов в .bobcache/:
     [wasm]   сборка C++ -> WASM (emcc); повторный запуск — 0.0 мс;
     [levels] прекомпиляция ВСЕХ 51 уровней НАСТОЯЩИМ парсером игры
              (Node-харнес tools/dump_levels.js со стабами DOM) ->
              engine/levels_cache.js; в игре parseLevel получает быстрый
              путь: сетка из base64 + готовые спавны вместо посимвольного
              разбора ASCII-карт;
     [verify] верификация: быстрый путь прогоняется по всем уровням и
              сверяется с шаблонами (сетка, символы, спавны, босс) —
              «ВЕРИФИКАЦИЯ OK: все 51 уровней совпадают»;
     [bench]  тест эквивалентности WASM <-> JS + бенчмарк;
     [fast]   сборка index.fast.html — WASM и кеш уровней встроены
              в один файл (ноль внешних запросов, офлайн).
   Сигнатура карт (FNV-1a) защищает от рассинхрона: отредактируете
   карты в map/editor.html — экспортированный maps.js изменит
   сигнатуру, и игра сама откатится на медленный (но всегда верный)
   путь, пока кеш не пересоберут. Стадии: python3 tools/smartcache.py.

ЧЕСТНЫЕ ЗАМЕРЫ (Node x64 в песочнице; телефон медленнее по CPU,
но выигрыши от нуля аллокаций и WASM там только больше)
────────────────────────────────────────────────────────────────────
• Эквивалентность: WASM и JS-двойник ПОБИТОВО совпадают на сценарии
  2000 шагов физики × 40 сущностей + 60 000 частиц + 500 solid-проб
  (tests/test_equiv.js).

• Бенчмарк ядра (micro): на десктопном Node JS-двойник даже чуть
  быстрее WASM (V8-компилятор отлично обрабатывает такие циклы,
  а каждый вызов через границу JS<->WASM стоит ~100-200 нс):
    физика:   WASM 0.75 мкс/ход  vs  JS 0.30 мкс/ход
    частицы:  WASM 3.2 мс/кадр   vs  JS 2.4 мс/кадр (30 тыс. частиц!)
  На телефоне разница в пользу WASM проявляется под нагрузкой:
  мобильные JIT слабее и чаще впадают в деоптимизации, а паузы GC
  (главная причина фризов на телефоне) в WASM-пуле отсутствуют
  полностью. Честная формулировка: микро-выигрыш физики зависит от
  устройства; гарантированный выигрыш — частицы без аллокаций/GC и
  стабильный кадр.

• Загрузка уровня (главный пользовательский эффект умного кеша):
    медленный разбор ASCII: 281 мкс/уровень
    быстрый путь из кеша:   103 мкс/уровень  (x2.7)
  плюс разовый прогрев ~20 мс на первом уровне сессии.
  На телефоне (медленный CPU) абсолютные числа больше, отношение
  сохраняется: каждый старт уровня и каждый рестарт после смерти
  становятся быстрее.

• Сборка проекта (умный кеш):
    холодная (с нуля):  emcc + дамп 51 уровня + верификация ≈ 1-2 мин
    тёплая (без правок): 0.21-0.27 с, из них 2-4 стадии — мгновенные
    попадания кеша (0.0 мс)

• Размеры:
    index.html        473 КБ -> 488 КБ (встроен JS-двойник + клей)
    index.fast.html  1018 КБ (WASM 10.5 КБ + кеш уровней ~520 КБ внутри)
    engine/bob_engine.js (WASM single-file) 10.5 КБ

КАК ПОЛЬЗОВАТЬСЯ
────────────────
• Просто играть: открыть index.fast.html (всё встроено, офлайн).
  Либо index.html рядом с папкой engine/ — эффект тот же.
• Пересобрать после правок карт/движка:
    python3 tools/smartcache.py        # из папки проекта
    python3 tools/smartcache.py --clean  # сбросить кеш
• Пересобрать только WASM (нужен emsdk): bash engine/build.sh
• Тесты: node tests/test_equiv.js        # эквивалентность + бенчмарк

ПРИМЕЧАНИЕ О «МИЛЛИОНЕ РАЗ»
───────────────────────────
Ускорение «в миллион раз» физически недостижимо ни для одного кода:
алгоритмы игры уже оптимизированы автором (запечённый слой тайлов,
фиксированный шаг физики, переиспользуемые прямоугольники). Реальный
эффект этой доработки: убран GC-мусор из горячего цикла (частицы),
горячая математика вынесена в WASM, загрузка уровня ускорена в ~2.7
раза, пересборка проекта из минут — в доли секунды. Все числа выше
получены запуском тестов в этой песочнице и воспроизводятся командами
из раздела «КАК ПОЛЬЗОВАТЬСЯ».
